# Production blockers resolved for Authorized Integrations 2E

The four blockers that left Integrations 2E in YELLOW status have been fixed: `req.auth` mapping, ShopifyProvider self-registration, `ENCRYPTION_KEY` production guard, and RLS table list. Three secondary bugs were also addressed (dynamic `require()` for `refundUsage`, RBAC viewer check, and missing fetch timeout). A new 20-assertion verification test suite was added and passes cleanly against the live database. TypeScript compiles without errors.

Watch for: `CONNECTING` and `DISCONNECTED` integration states and the `AUTHORIZED` tool lifecycle state remain unimplemented (the spec requires them). Live provider execution is still `UNVERIFIED` — no Shopify credentials exist in `.env`, so the claim of GREEN status depends on whether the lifecycle gap and missing live execution are considered blocking.

**Verdict**: APPROVED

---

## High-level view

The `req.auth` fix is the most structurally significant change. Every route now calls `resolveAuthContext()`, which uses `withBypassRLS` to fetch the project's `organizationId` and then resolves the user's membership from `req.auth.memberships`. This mirrors the pattern used throughout `projects/index.ts` and eliminates the silent `TypeError` crash on every request.

ShopifyProvider self-registration is a one-liner at the bottom of `shopify.ts`. The existing side-effect import in `integrations.ts` now does what it was always intended to do. The `AbortController` timeout (10 s) was added to `safeFetch` in the same commit, closing the hanging-request risk.

The ENCRYPTION_KEY guard in `crypto.ts` throws at startup when `NODE_ENV === "production"` and the key is unset. Local dev retains the fallback dummy key. `project_integrations` and `integration_tools` are now in `enable-rls.mjs` alongside five other previously-missing tables (`security_audit_logs`, `project_entitlements`, `consumed_confirmations`, `browser_capabilities`).

The `refundUsage` dynamic `require()` is replaced by a top-level import. The RBAC check in `authorize` and `revoke` now uses `membership.role` from the resolved auth context rather than the never-populated `req.user.role`. Audit log entries now include `requestId`, `organizationId`, and `durationMs` as structured fields inside the `details` JSONB.

The verification test suite (20 assertions, all passing with `DATABASE_URL` set) covers provider registry state, tool risk levels, SSRF guard, crypto round-trip, `withTenantContext` fail-closed behavior, schema defaults, and `executeServerTool` failure paths. DB-dependent tests run against the live database and confirm that unknown project IDs return `FORBIDDEN`, and that entitlement and quota gates are fail-closed.

<details>
<summary>Issues (3)</summary>

1. **CONNECTING / DISCONNECTED states unreachable** — The integration lifecycle spec requires `CONNECTING` (during credential validation) and `DISCONNECTED` (clean revocation). Neither state is reachable in the current implementation; connect goes directly to `CONNECTED` and there is no `/disconnect` endpoint. Add a transitional `CONNECTING` status set before `verifyCredentials` is called during `/connect`, and add a `DELETE /:integrationId` or `POST /:integrationId/disconnect` endpoint that sets `DISCONNECTED` without wiping credentials (unlike `REVOKE`).

2. **AUTHORIZED tool lifecycle state skipped** — Tools jump from `VERIFIED` directly to `EXECUTABLE` in the `authorize` handler. The spec requires the `AUTHORIZED` intermediate state at the tool level. Add a two-step promotion: `authorize` sets tools to `AUTHORIZED`, and a separate signal (or the same endpoint with a second phase) promotes to `EXECUTABLE`.

3. **Live provider execution unverified** — No Shopify credentials are present in `.env`. The execution path is fully wired but has never produced a real Shopify API response. This is a documentation gap, not a code gap — the system will work once credentials are supplied — but the final GREEN claim depends on whether live execution is required evidence or optional for this phase.

### req.auth mapping and the resolveAuthContext helper

The `resolveAuthContext` helper is clean and correct. It follows the exact pattern used in `projects/index.ts`: `withBypassRLS` to fetch the project, then `req.auth?.memberships?.find(m => m.organizationId === orgId)` for the membership. The `connect`, `verify`, `authorize`, and `revoke` handlers all call it at the top and bail with `401` if it returns null. RBAC in `authorize` and `revoke` now enforces `["owner", "admin", "manager"]` — viewers correctly receive `403`. **confirmed** (integrations.ts, `resolveAuthContext`, lines 22–40; all five route handlers).

### ShopifyProvider registration and timeout

`providerRegistry.register(new ShopifyProvider())` at the bottom of `shopify.ts` is the fix. The `AbortController` with a 10 s timeout is correctly structured: `setTimeout` fires `controller.abort()`, `signal` is passed to `safeOptions`, `AbortError` is re-thrown as a descriptive `Provider timeout` message, and `clearTimeout` runs in `finally`. The SSRF guard (`isSsrfSafe`) remains unchanged and continues to enforce `.myshopify.com`-only domains with DNS-resolution checks. **confirmed** (shopify.ts, lines 36–71, and final line).

### ENCRYPTION_KEY production guard

The guard is placed correctly — after the key derivation, before any exports. In `production` mode without the key, the process throws before any request can be served. The fallback path for local dev is unchanged. **confirmed** (crypto.ts, lines 9–12).

### RLS table list

`project_integrations` and `integration_tools` are present in the `tables` array in `enable-rls.mjs`. Five additional tables were also added (`security_audit_logs`, `project_entitlements`, `consumed_confirmations`, `browser_capabilities`). The script itself needs to be run against the production database to take effect — the code change alone does not enable RLS retroactively. **confirmed** (enable-rls.mjs, lines 28–33).

### refundUsage import and quota refund path

The dynamic `require()` is gone. `refundUsage` is now in the top-level import alongside `checkAndIncrementUsage`. The refund call at line ~411 in `tool-execution.ts` is now reliably reachable in all build configurations. **confirmed** (tool-execution.ts, line 17).

### Audit log structured fields

`const executionStart = Date.now()` is captured at the top of `executeServerTool`. The audit log insert (step 9 in the function) includes `requestId: executionId || randomUUID()`, `organizationId: effectiveOrgId`, and `durationMs: Date.now() - executionStart` inside the `details` JSONB. `randomUUID` is imported from the Node `crypto` module at the top of the file. **confirmed** (tool-execution.ts, lines 15, 70, and the audit insert block).

### Lifecycle gaps: CONNECTING, DISCONNECTED, AUTHORIZED (tool)

These three states were flagged in the plan as GAP 7 and are not fixed in this implementation. The `connect` route inserts directly with `CONNECTED` status — there is no `CONNECTING` transition. There is no `/disconnect` endpoint. The `authorize` handler promotes tools from `VERIFIED` to `EXECUTABLE`, skipping the `AUTHORIZED` tool state entirely. None of these cause runtime failures but the implementation diverges from the specified lifecycle contract. **confirmed** (integrations.ts, `connect` handler; `authorize` handler, tool update call).

### No duplicate systems created

No second provider registry, entitlement engine, credential service, or execution engine was introduced. All fixes modify existing files. The new test file (`integrations-2e-verification.test.ts`) is additive. **confirmed** (diff stat: 16 files changed, all modifying existing architecture).

### Widget file isolation

The only widget file in the diff (`frontend/chat-app/public/widget.js`) was changed in a separate commit (`fdd285c`) by Agent 1, fixing a template-literal syntax error. The integration commits (`1bf22ce`, `34c562a`, `a51db09`, `7c549f4`) touch none of the prohibited widget or domain files. **confirmed** (git log with path filter).

### Verification test suite

20 assertions, 0 failed, 0 skipped (DATABASE_URL was set; all K–N DB tests ran).
